> `NODE_COMPILE_CACHE`、自探节奏等运行时改动**都已回滚**（见 §9）；

# 启动计时链与启动耗时评估（2026-10-18）

> 用户反馈：「whale 每次启动都感觉有点慢，评估一下哪里能做下优化」。
> 本文记录**计时链怎么做的**、**基线时间线**、**已做的优化与结果**，以及**下一刀该切哪里**。

## 1. 为什么要专门做一条计时链

- `dshm-host.log` 有 **17 MB**、混着大量运行期请求日志（`IN-REQ`/`IN-DONE`），读一次要很久；
- 本机 `hilog` 读不到应用的 ArkTS 输出（见 `docs/98` §6）；
- ⇒ 需要**两个小的、只含启动阶段的文件**，一次读取就能还原"点图标 → 页面可交互"的完整时间线。

## 2. 设计

| 侧 | 位置 | 内容 |
|---|---|---|
| ArkTS | `<files>/diag-startup-ui` | `EntryAbility.onCreate` / 原生 `startHost` / `loadContent` / WebApp 阶段机 / 页面 onPageBegin/onPageEnd |
| Host | `<files>/dsh/home/diag-startup-host` | 既有的 `BOOT_00…BOOT_70` 阶段机（`stage()`）额外分流到独立文件，另带 `cc=`（V8 编译缓存状态） |

- 行格式（两侧一致）：`<epoch ms>\t+<相对该侧起点的 ms>\t<阶段名>[\t<附加信息>]`；
- 合并读取：`tools/read-startup-trace.py`（按 epoch 排序 → 时间线 + 相邻打点差 + 就绪总耗时）；
- **纪律**：所有打点 `try/catch` 包裹（失败绝不影响启动）、不写任何凭据、只打启动关键路径，不碰运行期热路径。
- 就绪判据：`APP_READY_TOTAL` = 官方 Web UI 首次 `onPageEnd` 且未判失败（只记一次）。

## 3. 基线（rc.2，冷启动，真机）

| 区间 | 耗时 | 占比 | 说明 |
|---|---|---|---|
| 0 → 0.26 s | 0.26 s | 2% | ArkTS `onCreate` → 原生 `startHost` 返回 |
| 0.26 → 0.61 s | 0.35 s | 3% | Host 进程启动 + 环境/核心树/profile 读取（`BOOT_00→BOOT_40`） |
| **0.61 → 9.13 s** | **8.5 s** | **76%** | **`runProfile`：插件树挂载 + dsh 初始化 + web server**（`BOOT_40→BOOT_65`） |
| 9.13 → 9.98 s | 0.85 s | 8% | auth url → `runProfile` 返回 → HTTP 自探 |
| 9.98 → 11.23 s | 1.25 s | 11% | ArkWeb 导航 + 官方 Web UI 首载（onPageBegin→onPageEnd） |

> 结论：**唯一的"大石头"是 `runProfile` 里的插件树挂载 8.5 s**，其余都是百毫秒级。
> 历史日志（`WebApp.ets` 启动页注释里 2026-09-27 的读数）也记过 `BOOT_40 → BOOT_65 = 7.2 s`
> ⇒ 这一项**不是 rc.2 的回归**，而是长期存在的成本。

## 4. 已做的优化尝试与结果

| # | 改动 | 结果 | 状态 |
|---|---|---|---|
| ① | `NODE_COMPILE_CACHE`（V8 编译缓存，`buildHostEnv` 注入，目录 `<home>/.v8-compile-cache`） | 真机 `BOOT_00` 显示 `cc=on:…`；两轮实测 `BOOT_40→BOOT_65` 8.4 → 8.5 s，**无显著收益**（jitless 下缓存收益有限） | **保留**（无害、后续观察） |
| ② | HTTP 自探间隔 500 → 50 ms（`probeHttpReady`） | `BOOT_63B→BOOT_70` 仍 0.49–0.65 s（服务端应答延迟占主导），收益 <0.1 s | **保留**（语义更合理） |
| ③ | ArkWeb 预热：BOOTING 阶段先挂 Web、`src=about:blank` | **事故：卡死 109 s**。`Web` 的 `src` 是**初始化参数、不是响应式属性** ⇒ 预热后 launchUrl 就绪时改 `src` 不触发导航，只能等自动重试（~119 s）走 `controller.loadUrl` 救回 | **已回滚**（教训写进 `WebApp.ets` 注释） |

**③ 的恢复件**：`dist/rollback/whale-rc.2-trace-v2-signed.hap`（336,795,020 B / sha256 `2412678e…`）
与 `dist/rollback/恢复指南.md`（App 起不来时怎么回装；覆盖安装不动会话数据）。

## 5. 下一刀切哪里（建议顺序）

1. **`runProfile` 的 8.5 s（唯一值得动的大头）**：
   - 首选 **`--cpu-prof` 采样**（Host 启动加 `--cpu-prof --cpu-prof-dir=<files>/prof`，用标志文件门控，跑一轮后按 URL/函数聚合）⇒ 直接看出是 ESM 解析、插件 `apply`、还是某几个重插件；
   - 若采样不可用（jitless 下的采样限制），退化为 **profile 层 A/B**：在设备树 `profiles/ondevice/cordis.patch.yml`（或 home 级 patch）逐组 `disabled: true`，每次重启读计时文件量化，可逆、不用重新出包。
   - 备选：插件树里必然有些"设备侧用不到"的插件（experimental / devtools / 多端相关），端侧 profile 裁剪是最直接的收益来源，但**要逐项确认功能不受影响**。
2. **1.25 s 的 Web UI 首载**：ArkWeb 缓存策略（`cacheMode`/预连接）可试，收益上限 ~1 s，风险低但要真机验证。
3. **观感**：启动页已有品牌动效 + 进度条；考虑按 Host 阶段更新文案（需要 Host → ArkTS 的轻量信号），让 11 s 更像"有进展"而不是"卡住"。

## 8. CPU 采样结果（2026-10-18，`inspector` 代码内采样，BOOT_00→BOOT_70 共 9.7 s）

采样方法：`<home>/enable-host-cpu-prof` 文件门控 ⇒ `main.js` 里 `Profiler.start()`（BOOT_00）→
`Profiler.stop()` 写 `<home>/prof/host-boot-<epoch>.cpuprofile`（BOOT_70 / fail / 25s 兜底）；
汇总工具 `tools/summarize-cpu-profile.py`（自耗时、按 npm 包聚合；带调用链分析）。

| 热点 | 自耗时 | 占比 | 解读 |
|---|---|---|---|
| `makeSyncRequest`（`node:internal/modules/esm/hooks`）+ 异步 0.10 s | **1.07 s** | **11.1%** | **自定义 ESM resolve 钩子（`module.register` 的 undici 垫片）**：钩子跑在独立 loader 线程，**每次模块解析**都要跨线程同步 IPC |
| `compileSourceTextModule` + `ModuleWrap` | 1.17 s | 12.0% | ESM 编译（jitless 下无 JIT，解析+编译更贵） |
| `<native/no-url>` | 2.48 s | 25.5% | V8/native 内部（含 fs、编译、GC） |
| `walkJsonValue` / `enumerableStringKeys`（`dsh-util-values`） | 0.25 s | 2.6% | 配置/投影 JSON 遍历 |
| `spawn` 合计 | **0.48 s** | 4.9% | `ensureExecutables` 0.23 s + `probeShellCapability` 0.21 s + market-bridge `shimRunnable` 0.04 s（**启动期 exec 探测**） |
| `js-yaml` | 0.44 s | 4.5% | profile/bundle patch 的 YAML 解析 |
| `@deepseek-ai/cordis` | 0.41 s | 4.2% | 插件框架本身 |

**判断：jitless 下"ESM 模块加载链路"≈2.5 s（钩子 IPC + 编译）是唯一的结构性大头**，其余是框架/配置解析的常态成本。

### 下一刀候选（按收益/风险排序）

1. **去掉 `module.register` 的 undici resolve 钩子**（预计 **−1.0~1.2 s**）：改为在核心树
   `node_modules/undici/package.json` 的 `exports` 里把 **`import` 条件**指向本仓 ESM 垫片
   （`require` 分支保持原生 undici 不动）。需要：pack-core 注入垫片 + `coreVersion` 升 `+whale.2`、
   更新 `check-web-fetch-jitless` 的判据（从"钩子生效"改为"exports.import 生效"）。
2. **启动期 exec 探测挪到就绪后异步**（预计 **−0.4~0.5 s**，低风险，只改 `main.js`）：
   `ensureExecutables`、`probeShellCapability`、market-bridge 的 `shimRunnable` 都是"给 UI 报能力"用的，
   不阻塞 Host 就绪；改为 `BOOT_70` 之后再跑（读数迟几秒写入 `host-ready.json` 即可）。
3. `js-yaml` / `dsh-util-values` 的解析成本属上游框架，收益小、改动风险高，暂不动。
