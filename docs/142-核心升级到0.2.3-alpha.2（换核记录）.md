## 六、真机冒烟发现并已修：PTC 模式「加载失败」

**症状**（Agent 预设页，2026-11-24）：`PTC 模式` 卡片报 `tool-executor-ptc (@deepseek-ai/dsh-tool-executor-ptc): waiting for ptcRuntime`；
宿主日志：`ptc-runtime-inproc (@deepseek-ai/dshm-ptc-runtime-inproc): failed to import: … does not provide an export named 'DUNDER_MEMBER'`。

**根因**（alpha.2 改了 PTC 缝的导出面）：

- `@deepseek-ai/dsh-ptc-runtime` 的导出从 `DUNDER_MEMBER / PORTABLE_RESERVED_WORDS / PtcRuntime / RESERVED_BINDING_GLOBALS / RESERVED_ERROR_MEMBERS`
  变为 `PTC_RUNTIME_ERROR_CODES / PtcImage / PtcInspectableValue / PtcRuntime / PtcRuntimeError / RESERVED_BINDING_GLOBALS / RESERVED_BINDING_WORDS / RESERVED_ERROR_MEMBERS`：
  **`PORTABLE_RESERVED_WORDS` 改名 `RESERVED_BINDING_WORDS`（48 词，只保留 ECMAScript 子集）**、**`DUNDER_MEMBER` 直接移除**
  （官方 node 实现改为只在 `scoped-repl` 格式下拒绝含 `__$binding_` 的名字）。
- 我们的同进程替代实现 `hostcore/plugins/dshm-ptc-runtime-inproc` 仍按 rc.5 导出 import ⇒ ESM 链接期直接失败 ⇒ `ptcRuntime` 服务缺失 ⇒ 依赖它的 `optional-ralph-workflow` 与 `tool-ralph` 一起 pending。
- `IDENTIFIER` 口径也变了：alpha.2 官方实现为 `/^[A-Za-z_$][A-Za-z0-9_$]*$/`（允许 `$`），rc.5 及以前不含 `$`。

**修法**（`hostcore/plugins/dshm-ptc-runtime-inproc/lib/index.js`）：

1. import 改为 alpha.2 的导出名（`RESERVED_BINDING_WORDS`），删除 `DUNDER_MEMBER` 的 import；
2. `IDENTIFIER` 跟上 alpha.2 官方口径（允许 `$`）；
3. **`DUNDER_MEMBER = /^__.+__$/` 在本地保留**（缝不再导出，但错误成员名的拒绝语义按 rc.5 不动）；
4. **`PORTABLE_RESERVED_WORDS` 在本地重建**：`RESERVED_BINDING_WORDS ∪ 23 个 Python 侧撞名词`（`lambda`/`def`/`None`/`True`…）
   ⇒ 对外行为与 rc.5 逐字一致（门禁 `check-ptc-runtime-inproc` 的 C13 判据就是"`lambda` 必须照样被拒"）。

**验证**：`check-ptc-runtime-inproc`（165 断言）PASS、`check-ptc-wiring` PASS、`check-ptc-ts-strip` PASS；coreVersion 递增为
**`0.2.3-alpha.2+whale.2`**（核心树内容变了就必须递增），新容器 `169,428,553 B` sha256 `3a49b1df…`；验证件重出为
`whale-verify-alpha2-whale2-vc1010001.hap`（463,496,653 B，sha256 `ad528e2d…`）并覆盖装机。

## 八、真机冒烟发现并已修：三方插件统一失效（`connection.requestRejection` 被删）

**两个症状，同一个根因**（2026-11-24）：

- 文件面板 `HTTP 400`：`POST /sidebar/api/*` 全部方法（连 GET 也 400、0–1ms、**空响应体**）；
- 插件市场：`/dsh-market/*` 全部 403 `untrusted origin`，页面「插件目录加载失败」，点「更新插件市场」也没救；
- 宿主日志无异常行（异常被 webserver 兜底成 400 空体）。

**根因**：DSH 0.2.3（我们升到的 alpha.2）删除了 `ctx.connection.requestRejection(request)`，改为
`admit(request) → { peer } | { rejection }`。而端侧用户装的三方插件仍按旧 API 调用：

| 插件 | 调用点 | 现象 |
|---|---|---|
| `dsh-better-sidebar@0.32.1` | `const fence = req => ctx.connection.requestRejection(req) === undefined` | 每个 `/sidebar/api/*` 请求在 fence 里抛 TypeError ⇒ webserver 兜底 **400 空体** ⇒ UI 只显示「HTTP 400」 |
| `dshmarket@1.80.1` | host gate 优先 `requestRejection`，缺失时走 `admit` fallback | `/dsh-market/*` 全部 **403 untrusted origin** |
| `dsh-whale-widget@0.4.x` | 同类调用 4 处 | 部分路由失效（`/dsh-whale/*` 的 GET 尚可） |

**修法**：不改用户插件（会被插件更新覆盖），在宿主启动层补回旧 API —— `hostcore/app/main.js` 新增
`installPluginCompatShims(ctx)`，在 `runProfile` 返回、拿到 `ctx` 后执行：若 `connection.requestRejection`
缺失，则按 rc.5 原始语义补一行等价方法：

```js
conn.requestRejection = function (request) {
  const admission = this.admit(request);
  return admission && typeof admission.rejection === 'number' ? admission.rejection : void 0;
};
```

alpha.2 的 `admit(request)` 接受含 `headers`/`socket` 的请求对象，认证 provider 只读 `headers`，直接传 node request 即可；
已有的上游实现不会被覆盖（只补缺失）。真机验证：两个插件的接口恢复正常。

**产物**：`place-host-app` 同步 19 件 + `assert-resfile-sync` PASS；补丁门禁 173/0；
验证件重出为 `whale-verify-alpha2-whale2b-vc1010001.hap`（**463,496,651 B**，sha256 `4273289a…`，内含
`installPluginCompatShims`）并覆盖装机。coreVersion 不变（`0.2.3-alpha.2+whale.2`，核心树本身没再改）。

**排查记录（可复用的手法）**：真机 host 起来后，可用宿主自带的 Python 桥读 app 沙箱：
`GET /dshm-python/run-get?token=<dsh web token>&code=<python>` 带上 `dsh-auth` cookie ⇒ 能列/读 `$DSH_HOME`
（含用户插件源码、profile 的 `package.json`），这是 dsh/home 0700 权限下唯一可用的读取通道（bridge 见 `docs/120`）。


## 九、真机冒烟发现并已修：Office 预览 `conversion failed (HTTP 401)`

**症状**（2026-11-24 14:06）：docx/pptx 侧栏预览 →「读取失败：conversion failed (HTTP 401)」；
宿主日志：`POST /dshm-office2pdf/convert conn=keep-alive cookie=(none) origin=undefined ua=undefined → 401`。

**根因**：alpha.2 给 `ctx.webServer.register()` 增加了**逐路由 auth 策略**，缺省 `auth ?? "required"`
（rc.5 的 `dsh-host-webserver` 根本没有这层授权）。而 `dshm-office2pdf` 宿主插件按设计是**进程内 Node fetch
自调用** HAP 的转换端点（无 cookie）⇒ 被宿主自己的登录检查挡成 401，转换从未执行。

**修法**（`hostcore/app/main.js`）：把 HAP 自己在 `ctx.webServer` 上注册的 **6 个端点**显式标成 `auth: "anonymous"`：

| 端点 | 调用方 / 自带校验 |
|---|---|
| `/dshm-office2pdf/convert` | 插件宿主半边 Node fetch；路径白名单（沙箱 / `$HOME` / 用户存储） |
| `/dshm-python/{status,run-get,exec}` | 宿主/工具链；run-get/exec 有 token 校验（`pyBridgeTokenOk`） |
| `/dshm-registry/view` | `$HOME/bin` 的 pnpm/npm 假壳；token 校验 |
| `/dshm-packages/list` | 插件安装通道；自校验 |

安全性：`anonymous` 只跳过"登录 cookie"，**Host/Origin 栅栏仍生效**（alpha.2 的 `webserver/authorize`
hook 在 anonymous 分支前先跑 connection 的 `isTrustedRequest`）；这些端点本身只监听 loopback，
且各自还有 token 或路径白名单。

**产物**：`place-host-app`（19 件）+ `assert-resfile-sync` PASS；验证件
`whale-verify-alpha2-whale2d-vc1010001.hap`（**463,504,848 B**，sha256 `8f74d86c…`，HAP 内 main.js
含 6 处 `auth: "anonymous"`）已覆盖装机。

**教训（alpha.2 升级面）**：`webServer.register` 的默认 auth 从"无"变成"required"是这一版**最隐蔽的
破坏性变更**：所有"宿主自己注册、非浏览器调用"的端点都会 401，表现为各功能各自的「HTTP 401」，
根因同一处。以后升级要专门过一遍 main.js 里 `ctx.webServer.register` 的每一处。


## 十、真机冒烟发现并已修：新版 Web UI「全都看不到」

**症状**（2026-11-24 14:22）：文件面板/插件市场修好后，用户反馈 alpha.2 的新 UI（会话面板、已读未读、连接器账号、远程连接）**一个都看不到**。

**两个叠加原因**：

1. **ArkWeb 缓存把前端钉在旧版本**：宿主对前端静态资源的响应是
   `cache-control: public, max-age=31536000, immutable`（服务端用内容哈希做 `?rev=`）；
   换核后入口 HTML 会刷新，但模块清单/插件 bundle 仍可能命中旧副本 ⇒ 跑的一直是旧前端。
   证据：`diag-web-console` 里加载的模块清单仍是旧 rev（`plugins/??…&rev=1640a16353ed`），
   而当前宿主提供的是新清单。
2. **`dsh-proxyagent` 用了 alpha.2 已改的槽位 API**：它给 `plugins.item`（**list** 槽）注册时
   仍传 `{ key: PKG }`（旧 keyed 语义），alpha.2 要求 list 槽必须给 `options.id` ⇒ 模块初始化时
   直接 `Uncaught Error: list slot "plugins.item" requires options.id`（`diag-web-console` 的 L4 行），
   该模块及其后续注册失效。

**修法**：

- `entry/src/main/ets/pages/WebApp.ets`：
  · 新增 `ensureWebCacheFreshForCore()`：启动时用 `filesDir/web-cache-core-version` 记录的**核心版本指纹**
    判断，换核后调 `webview.WebviewController.removeAllCache(true)` 清一次缓存（只清一次，不拖慢日常启动）；
  · 新增菜单「**强制刷新（清缓存）**」（应用菜单 → 强制刷新）供插件更新后手动清；
  · 在 `aboutToAppear()` 里先清缓存再载入页面。
- `dsh-proxyagent`（用户插件，装在 profile）：把 `plugins.item` 的注册从 `key:` 改成 `id:`
  （设备上已改，备份 `lib/client.js.bak-dshm-20261124`）；**工作区源码**
  `Common/ProxyAgent/plugin/dsh-proxyagent/lib/client.js:516` 同样待改（等用户决定是否发版）。

**教训**：alpha.2 还有第三处破坏性变更 —— **插槽契约**：`plugins.item` 从 keyed 变 list，注册必须给 `id`。
配合 §八（`requestRejection` 删除）与 §九（webServer 默认 auth），这类"插件面 API 漂移"是本版升级的主要成本。

## 十一、官方「远程连接」启用（局域网绑定 + 面板恢复，2026-11-24）

**背景**：用户验收时问"在哪里打开远程访问的设置"。核实结论不是版本旧、也不是缓存，而是端侧**自身**把它关掉了，且 Host 绑回环使功能即使出现也不可用。

### 11.1 upstream 事实（逐条读代码确认）

| 事实 | 证据 |
|---|---|
| 功能在 UI 里叫「**远程连接**」（`settings.section` id `remote-connection`，order 25，夹在「通用」与「模型」之间；面板含「访问地址」「二维码登录」「复制登录链接」「配对申请审批」） | `node_modules/@deepseek-ai/dsh-client-remote-connection/locale/zh.json`、`lib/client.js` 的 `zh` 字典与 `ctx.slots.register({name:'settings.section',id:'remote-connection'…})` |
| 面板可用性由 Host **监听/广播地址**决定，没有 UI 开关 | `dsh-client-remote-connection/lib/index.js` 的 `deployment()`：`hostname` 为 `localhost`/`::1`/`127.*` ⇒ `availability:"unreachable-host"`；非回环且 `webserver/authorize` 放行 ⇒ `available` |
| 让远程可用的唯一官方途径是启动参数 | `dsh-web-app/lib/startup.js`：`--host <一个具体本机接口地址>`（`isWildcardHost` 明确拒绝 `0.0.0.0`）、`--trusted-host <host[:port]>` 可重复 |
| Web 面板在"桌面载体"下被主动跳过 | `dsh-client-remote-connection/lib/client.js` `apply()`：`await ctx.remote.$mount(TYPERT_REMOTE); if (`dshDesktop`in globalThis)return;` |

### 11.2 根因（为什么 Whale 里看不到）

1. `entry/src/main/ets/pages/WebApp.ets` 的 `DESKTOP_CARRIER_JS` 在文档开始时注入
   `globalThis.dshDesktop={protocolVersion:1}`（当初为了让左下角账号菜单 / 设置里的账号节出现）。
2. 上面那行 `if(`dshDesktop`in globalThis)return;` 命中 ⇒ 远程连接的**整个设置节不注册**，界面上毫无痕迹。
3. 即使注册了，Host 启动参数写死 `--host 127.0.0.1`（`hostcore/app/main.js` 的 args）⇒ `deployment()` 判
   `unreachable-host`，面板只会显示"当前地址无法用于跨设备登录…"。

### 11.3 本次改动（用户决定：同步官方功能，本地"只绑回环"的策略让位）

- **`hostcore/app/main.js`**
  · 新增 `localIPv4Addresses()` / `BIND_HOST`：取本机局域网 IPv4（`wlan*/eth*/en*` 优先，排除 `169.254/16`）；
    没有局域网地址时回退 `127.0.0.1`（应用照常可用，远程连接降级为不可用）。
  · 启动参数改为 `--host ${BIND_HOST}`，`--trusted-host` 同时给 `127.0.0.1:PORT` 与 `${BIND_HOST}:PORT`
    （栅栏判定口径见 `dsh-web-app/cordis.patch.yml` 的 `connection` 行注释：回环 / 监听地址 / trustedHosts 三者可信）。
  · 新增 `probeBindable()` 预检：局域网地址若绑不上（网卡状态/平台限制）→ 记日志并**回退回环再启动**，
    避免"核心起不来"这种用户无法自救的失败形态。
  · 新增 `startLoopbackBridge()`：`127.0.0.1:PORT → ${BIND_HOST}:PORT` 纯 TCP 双向管道（HTTP/SSE/WebSocket 都通），
    **在 dsh 已监听之后**才起。作用：ArkTS 就绪探测（`NodeRuntime.portAnswers` 写死 127.0.0.1）与既有回环接线继续可用；
    桥只绑回环 ⇒ 局域网连不进来（不把"本机自连"判据变成外部入口）。
  · **收紧 6 个 HAP 端点的 auth**：原先一律 `auth:'anonymous'`（为无 cookie 的本机 fetch 放行）。
    远程连接一开，Host 就在局域网上，若不区分来源，任何同网段设备都能直接调 `/dshm-python/exec`（等于绕过配对
    审批执行任意代码）。改为 `auth: selfOnlyAnonymous`：**来源是本机（回环或本机网卡地址）才 anonymous，其余
    required**（回落到 dsh 浏览器 cookie 栅栏，必须先完成配对/登录）。涉及 `/dshm-office2pdf/convert`、
    `/dshm-python/{status,run-get,exec}`、`/dshm-registry/view`、`/dshm-packages/list`。
  · `runtimeFacts().listenAddress` 改为实际绑定地址（`ACTIVE_BIND_HOST`），设置页/诊断读数不再写死 127.0.0.1。
- **`tools/pack-core.mjs`**：新增 `patchRemoteConnectionDesktopGate()`（⑲）——只删
  `if(`dshDesktop`in globalThis)return;` 这一处提前退出，保留 Web 版设置节。标记 `DSHM_REMOTE_CONNECTION_DESKTOP_GATE`；
  锚点漂移直接 `die`，不静默跳过。
- **`tools/check-core-openharmony-patches.mjs`**：注册 ⑲ 的四条判据（标记 ×1、`settings.section` 座位在、
  `id:remote-connection` 在、上游提前退出原文已消失），门禁 173→**177** 条；`--self-test` 自动覆盖 ⑲ 的变异用例（4 条）。
- **`entry/src/main/ets/pages/Index.ets`**：核心页「监听地址」不再把非回环判成 warn（口径改为"局域网优先、回环兜底"）。
- **`hostcore/core-recipe.json`**：`coreVersion` → **`0.2.3-alpha.2+whale.3`**（核心树内容变了，必须递增 build metadata）。

### 11.5 用户验收口径（重启应用后）

1. 设置 → 左侧应出现「**远程连接**」（在「通用」之后、「模型」之前）。
2. 进入后「访问地址」应显示 `http://192.168.1.60:3122`（同一 Wi-Fi 变更后地址会变，重启应用即重新取）。
3. 「二维码登录」/「复制登录链接」是**两条"直接登录"通道，不经过审批**：二维码是一次性凭据
   （`tickets.consume` 用掉即失效）、登录链接里就是本机启动 token；拿到任一个的浏览器**直接**获得
   完整访问权限（面板红字警告原文就是这么写的："二维码使用或过期前，持有它的人都可以登录"、
   "此链接包含登录凭据…重启服务后链接失效"）。这是 2026-11-24 用户实测确认的行为：
   手机扫码、另一台机器打开带 token 的 URL 都**直接进入**，本机不会出现任何配对申请。
4. **「配对申请」是第三条、独立通道**（不是扫码的必经环节）：另一台设备打开**不带凭据**的
   `http://<本机地址>:<端口>/` 时，登录页会给出「连接到此 Host」+「配对此设备 / 申请配对」按钮
   （匿名页 `pairing/client.js` 挂载 `<dsh-device-pairing>`）；对方点「申请配对」后页面显示
   **配对码**并"正在等待批准"，此时**本机**「设置 → 远程连接」才出现「配对申请」列表，
   核对配对码后「批准/拒绝」，批准后对方自动登录。
   官方 zh 原文：pairHint「申请后，在另一台已登录设备的"设置 → 远程连接"核对配对码并批准，此设备将自动登录。」
5. 所以"没有配对操作"不是故障：扫码/链接本来就不需要审批；要验证配对通道，用第 4 条的裸地址路径。
4. 若面板显示"当前地址无法用于跨设备登录"：说明启动时没拿到局域网地址（离线/网卡未起）或预检回退，
   查 `node-output.log` 的 `args=` 与 `回环桥` 行。

### 11.6 风险 / 回退

- **风险（用户已明确接受，选择"同步官方功能优先"）**：Host 暴露在同网段 ⇒ 同网段设备可尝试配对（需本机批准）；
  首次批准后该浏览器拥有完整权限（可再批准其它设备）。本机自定义端点已按来源收紧（§11.3 最后一条）。
- **回退**：`coreVersion` 改回 `0.2.3-alpha.2+whale.2` + `tools/pack-core.mjs` 里去掉 `patchRemoteConnectionDesktopGate()`
  调用（或直接把 args 的 `--host` 改回 `127.0.0.1` 即可让远程连接回到不可用而其余不变）→ 重出 HAP 覆盖装。
