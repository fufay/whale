# 插件安装器：依赖冲突不再覆盖根，改"嵌套 + 安装后体检"

> 2026-10-23 | 对应事故：`DSHM问题汇总与解决/issue-插件依赖被扁平安装互相覆盖.md`
> 涉及文件：`hostcore/app/dshm-installer.js`、`hostcore/app/dshm-user-rows.js`、`tools/check-dshm-installer.cjs`
> 产物：HAP `336,800,119 B`（`entry/build/default/outputs/default/entry-default-signed.hap`，2026-10-23 23:00 构建）

## 一、修的是什么

**根因（事故原文）**：安装器是**纯扁平落位**——所有依赖都落 `profiles/ondevice/node_modules/<name>`，
同名只留一份；后装的包要求不同版本时**直接替换根上那份**（日志：`已装版本漂移（js-yaml：磁盘
5.5.0 ≠ 目标 4.3.2），清除旧目录并重新落位`）。于是：

- `dsh-config-manager@0.1.81` 要 `js-yaml ^5.4.1`（v5 的 `NOT_RESOLVED` API）；
- `dshmarket@1.69.0` 要 `js-yaml ^4.3.2`；
- 装后者把根换成 4.3.2 ⇒ 前者下次启动 `SyntaxError: … does not provide an export named
  'NOT_RESOLVED'`；市场把"在 bundles 里但没热挂载"显示成"重启后生效" ⇒ **提示永远消不掉**。
  同一机制 10-21 / 10-23 各来一次（js-yaml v4/v5 与 argparse 3/2 一起翻）。

**新语义（对齐 npm/pnpm 的 dedupe + 嵌套，而不是"只留一份"）**：

| 场景 | 落位 |
|---|---|
| 顶层插件（depth=0） | 恒落 `node_modules/<name>`（用户请求谁就更新谁） |
| 依赖，根上**没有**同名包 | 落根（保持扁平，避免整棵树变深） |
| 依赖，根上有且**满足** range | **复用**（真 dedupe：不下载、不动盘；顺带校验包完整） |
| 依赖，根上有但**不满足** range | 落 `<消费者>/node_modules/<name>`（**不碰根**，别的插件照旧解析根上那份） |
| 依赖，根上有但半残 | 重落根自愈（不把坏包当依赖交出去） |

细节判据：`seen` 按**落位路径**去重（同名包可合法存在多份）；落位后的完整性校验从"profile 根上的
包名"改成"**这个 dest 目录**"（嵌套包不在根上，按根校验会解析到别的版本 → 假通过）；依赖的幂等
判据从"目标版本完全相等"改成"现有版本**仍满足 range**"（不为了追 latest 反复重下，避免"装插件"
变成"静默升级整棵依赖树"）。顶层仍按"目标版本漂移"判（用户请求了具体版本，必须收敛）。

## 二、安装后依赖体检（`depWarnings`）

安装完成的 `.done` JSON 新增 `depWarnings`：`[{pkg, dep, range, found, from}]`，空数组 = 通过。
它遍历 profile 里**每个顶层插件**声明的**必装依赖**（`dependencies`；optional 装不上属预期、
peer 本来就不装），按 Node 解析顺序（逐层向上找 `node_modules/<dep>`）核对解析到的版本是否满足
range；不满足/缺失的写进结果并打进宿主日志（`[installer] 依赖体检：…`）。

这样"某个插件因为别人的安装而解析到错版本"不再只能等下次 import 崩；市场/skill 侧可以直接
指出"**哪个包、要什么版本、实际解析到哪**"。体检是诊断，不参与落位，失败不影响安装结果。

## 三、验证（可重放）

### 3.1 事故组合（真实 registry，一次跑通）

临时 profile：先装 `dsh-config-manager@0.1.81`（根 js-yaml → 5.5.0），再装 `dshmarket@1.69.0`：

```text
依赖版本冲突（js-yaml：根上 5.5.0 不满足「^4.3.2」，改落嵌套 node_modules/dshmarket/node_modules/js-yaml）
依赖版本冲突（argparse：根上 3.0.3 不满足「^2.0.1」，改落嵌套 …/js-yaml/node_modules/argparse）
root js-yaml still 5.5.0   ✅（不再被降级）
dshmarket 解析到自己嵌套的 4.3.2   ✅
dsh-config-manager 能 import v5 的 NOT_RESOLVED   ✅
depWarnings = []   ✅
```

反向顺序（先 dshmarket → 根 4.3.2，再 config-manager → 嵌套 5.x）同样通过。
另用 `dsh-config-manager` + `cosmiconfig@8.3.6`（js-yaml ^4.1.0，小依赖树）做了可进门的快速回归。

### 3.2 门禁与负测试

`tools/check-dshm-installer.cjs` 新增三组（网络部分在能连 registry/codeload 的环境跑）：

- §7b `versionSatisfies` 纯函数 16 组（`^ ~ * 精确 >=/< || 前缀 0.x`）；
- §8i 安装后体检三向（只报不满足者 / 嵌套副本消除告警 / 嵌套版本错也报）；
- §10 冲突嵌套集成：先 `dsh-config-manager@0.1.81` 再 `cosmiconfig@8.3.6`，断言根不动、
  嵌套 4.x、`installed[]` 带 `parent`、两个消费者按 Node 解析各得其所、`depWarnings` 为空。

**负测试**：把旧版 `dshm-installer.js`（`git show HEAD~:…`）放临时目录跑同一冲突用例
⇒ 5 条断言红（根被换成 4.3.2、无嵌套、消费者解析到根、`depWarnings` 缺失），证明门禁有牙。

## 五、回退

- 旧 HAP：`dist/rollback/whale-rc.2-whale.2-cacheclean-signed.hap`（本轮构建前已装版本，逐字节复制）。
- 代码：`git revert` 本轮提交即可（安装器是 HAP resfile 资源，回退 = 重装旧 HAP）。
- 文件级：删掉 `…/<插件>/node_modules/<冲突依赖>` 即回到"单一根版本"（会恢复旧故障，仅用于对照）。

## 六、未做（有意）

- **不自动修** `depWarnings` 里的历史欠账（联网自动装会把"装一个插件"变成"改一堆别人的目录"）；
  体检只报告，修复走重装该插件或 `profile-dep-guard.mjs --fix`。
- **不实现 lockfile / peerDependencies / 多版本求解器**：端侧只需要"别把别人的依赖换掉"，
  嵌套两层即可表达；完整求解器在这个进程内安装通道里没有收益，只增加失败面。
- 市场「立即重启」只能关闭应用（`spawn(process.execPath)` 被 DSHM 兜底拒绝，`helper=-1`）——
  平台限制，与本修复无关。
- 本轮只改 HAP resfile（`hostcore/app/*` 经 `place-host-app` 进包），**不在核心树里**，
  故 `coreVersion` 保持 `0.2.1-rc.2+whale.2` 不动（口径同 `docs/106` 的说明）。
