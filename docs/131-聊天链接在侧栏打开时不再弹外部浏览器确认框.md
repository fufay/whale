# 131 · 聊天/侧栏网页里的链接不再弹「打开外部浏览器？」

日期：2026-11-03 · 范围：**新 Whale**（`com.jwhsoft.whale`）· 改动文件：`entry/src/main/ets/pages/WebApp.ets`（`OPEN_LINK_SHIM_JS`）

本次同一处代码连续修两件事，都是**壳的外链兜底多管了一手**：

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 聊天里点链接：**侧栏已打开**，还弹「打开外部浏览器？」 | 上游锚点 onClick 自己 `preventDefault` 后开侧栏，壳垫片在**捕获阶段**又投一次 `confirm` | 监听改**冒泡** + `if (ev.defaultPrevented) return` |
| 2 | 侧栏浏览器里点「弹新窗」的链接（B 站视频等）也弹框 | 侧栏是应用自己开的 iframe；端侧 `multiWindowAccess=false` 弹不出真窗，旧逻辑一律落到 confirm | 子框架里的 `window.open` / `_blank` 改为**在当前侧栏 tab 内自跳转** |
| 3 | 上面这版之后：侧栏页面**卡在无限刷新**，地址栏不动、页面不可用 | 站点的防 iframe 脚本在文档早期 `window.open(location.href)`；自跳转又是新文档、新垫片 ⇒ 自我循环 | 自跳转加两道闸：**同址不跳** + **必须有 1.5s 内的真实点击手势** |

---

## 一、现象

### 1.1 第一处：聊天正文点链接（2026-11-03 上午）

在聊天里点一条 http(s) 链接：链接**确实在右侧边栏的浏览器 tab 里打开了**，但同一次点击还弹了
ArkUI 的确认框「打开外部浏览器？」，点「打开」就再开一份系统浏览器 —— 一次点击开两处。
用户判定为 bug：**设置里如果是「在侧边栏打开链接」，就不要弹那个提示框。**

### 1.2 第二处：侧栏网页里点「弹新窗」的链接（2026-11-03 晚）

修完第一处后，聊天里的链接不再弹框；但在**侧栏浏览器里**打开 B 站列表、点任意视频
（站内本来就是 `target=_blank`／`window.open` 弹新窗），又弹「打开外部浏览器？」。
桌面 Web 形态下这里弹的是真浏览器窗（iframe sandbox 带 `allow-popups-to-escape-sandbox`），
端侧 ArkWeb `multiWindowAccess=false` 弹不出来，于是掉到同一个 confirm 兜底。

### 1.3 第三处：自跳转把页面变成了无限刷新（2026-11-03 22:20）

第二处装上后，侧栏里点链接确实不出确认框了、也能在当前 tab 跳转，但**之后页面一直卡刷新**、
地址栏 URL 不变、页面不能用。新 Whale 的 `files/diag-web-console` 抓到铁证（每 ~250ms 一轮）：

```
14:20:38.424Z [dshm-link] shim installed
14:20:38.520Z [dshm-link] subframe navigate https://www.bilibili.com/video/BV17cxC6QEsx/?spm_id_from=…
14:20:38.715Z [dshm-link] shim installed
14:20:38.809Z [dshm-link] subframe navigate https://www.bilibili.com/video/BV17cxC6QEsx/?spm_id_from=…
14:20:38.995Z [dshm-link] shim installed
14:20:39.088Z [dshm-link] subframe navigate https://www.bilibili.com/video/BV17cxC6QEsx/?spm_id_from=…
```

同一 URL 反复 → 说明不是插件重载，而是**页面自己**在每个新文档里再次请求同一个地址 ——
B 站有防 iframe／弹新窗脚本，文档早期就调 `window.open(location.href)`；第一版自跳转把它当成
「用户要在这里跳」，于是跳到同一页 → 新文档 → 又调 → 死循环。而且跨文档后垫片的 800ms 去重
（文档内状态）根本不跨文档，拦不住。

## 二、第一处：为什么会双开

### 2.1 上游这一侧（对的）

聊天正文的链接由上游 Markdown 渲染成 `<a target="_blank" rel="noopener noreferrer">`，其 `onClick`
自己会 `preventDefault()` 再按设置分流（`dsh-web-frontend/dist/assets/index-*.js` 里的锚点组件，
压缩后名 `rU` / `sU`；逻辑与 `dsh-client-ui-chat/lib/client.js` 的 `openExternalLink` 对应）：

```js
// 设置 store：linkOpening（"sidebar" | "new-tab"，缺省按 "sidebar"）
if (linkOpening.getSnapshot() === "sidebar"
    && ctx.get("sidebarRightTabs")?.get("browser") !== void 0)
  ctx.sidebarRight.openTab("browser", { params: { url } });
else
  window.open(url, "_blank", "noopener,noreferrer");
```

侧栏浏览器 tab 已在本档启用（`hostcore/profile` 的 `ui-sidebar-browser`，官方默认只给 desktop），
所以 `sidebarRightTabs.get("browser")` 存在 ⇒ 上游走的是**侧栏**，行为正确。

### 2.2 我们这一侧（错的）

`WebApp.ets` 的外链垫片为了修「点了没反应」（ArkWeb `multiWindowAccess=false`，`window.open` /
`target="_blank"` 一律被丢弃），在**捕获阶段**给 `document` 挂了 click 监听：看到
`a[target="_blank"]` + http(s) 就投 `openExternal(url, 'confirm')` 并 `preventDefault()`。
它**不 stopPropagation**，于是上游的 onClick 照样跑 —— 一次点击两条路都走：

| 顺序 | 谁 | 结果 |
|---|---|---|
| 1 | 壳垫片（捕获） | 弹「打开外部浏览器？」→ 用户点「打开」则系统浏览器再开一份 |
| 2 | 上游锚点 onClick（冒泡） | `preventDefault()` + 侧栏浏览器 tab 打开 |

`linkOpening === "new-tab"` 时还会更糟：捕获兜底弹一次，上游 `window.open` 又被垫片包了一层再弹一次
（两个一样的框）。

## 四、修法

### 4.1 第一处：页面自己接管过的点击，壳不再兜底

1. `document.addEventListener('click', …, true)` → `false`（改冒泡）：必须等页面 onClick 跑完才能读到
   `defaultPrevented`。
2. 监听体第一句：`if (ev.defaultPrevented) { return; }`。上游锚点一定 `preventDefault` ⇒「侧栏打开」
   这条路上壳彻底不出手；页面**没**接管的点击（「联系我们」裸锚点、AccountSection 授权锚点）
   `defaultPrevented` 仍为 false，照旧弹确认 / 自动外开。
3. `out()` 里给 confirm 加 1.5s 同 URL 去重（`lastConfirm`）：万一还有第二条兜底同时命中，不叠第二个框。

判据故意**不是**「去读设置项是不是 sidebar」：设置项在 web 侧 store 里，壳读不到；而侧栏 tab 不可用
时上游正好退化成 `window.open`，垫片的 `window.open` 包装仍接得住 —— 用「页面接管没有」做判据
自动覆盖两种情形。

### 4.2 第二处：子框架里的「新窗」在侧栏内跳转

新增 `inSubframe()`（`window.top !== window`；跨源抛错也按子框架处理）与 `navigateHere(url)`
（`location.assign` + 800ms 同 URL 去重）：

- 路径 2（click）：子框架里未接管的 `a[target="_blank"]` ⇒ `preventDefault()` + `navigateHere(href)`；
- `window.open` 包装：子框架里 ⇒ `navigateHere(url)` 并返回 `null`。

顶栏（应用主体）行为完全不变。**注意这是「同一个侧栏 tab 内跳转」，不是「再开一个侧栏 tab」**：
插件 `IframeImpl` 的应用已知历史仍可后退，但地址栏会显示插件的「URL 已变化」态（非应用发起导航的
既有表现）。要真正的「侧栏新 tab」需要让 web 侧插件能收到壳的信号（新增 client 插件 → 改核心树
→ 升 `coreVersion` + 重出包），风险/成本都更高，本次不做。

### 4.3 第三处：自跳转的两道闸

`navigateHere()` 现在按顺序判：

1. **手势闸**：`Date.now() - lastGestureAt > 1500` ⇒ 跳过（`subframe skip no-gesture`）。
   `lastGestureAt` 在**捕获阶段**记账（只认 `ev.isTrusted`），早于站点自己 onClick 里的
   `window.open`，所以「用户点了视频」仍然算手势；而**加载期/定时器里**的 `window.open`
   （防嵌套脚本、广告、登录弹窗）不算，一律不跳。
2. **同址闸**：目标与当前文档同 origin+path+search（忽略 hash）⇒ 跳过（`subframe skip same-url`）。
   直接掐断「跳到我自己」这一类循环。
3. 仍保留 800ms 同 URL 去重（锚点 + `window.open` 同一次点击常常都调）。

## 六、遗留（不是本次改动引入）

1. 侧栏浏览器 tab 是**沙箱化 iframe**（官方 Web 形态；desktop 才走 Electron `WebContents`）。
   `X-Frame-Options` / CSP `frame-ancestors 'none'` 的站点（GitHub 等）在侧栏里**永远白页**（§三 第二行日志）。
   这类链接只能走系统浏览器 —— 侧栏工具栏自带「在系统浏览器中打开」。
2. 「侧栏新 tab」取代「同 tab 跳转」是功能课题（见 §4.2 末），要动核心树。
