# 131 · 聊天链接在侧栏打开时不再弹「打开外部浏览器？」

日期：2026-11-03 · 范围：**新 Whale**（`com.jwhsoft.whale`）· 改动文件：`entry/src/main/ets/pages/WebApp.ets`（`OPEN_LINK_SHIM_JS`）

## 一、现象

在聊天里点一条 http(s) 链接：链接**确实在右侧边栏的浏览器 tab 里打开了**，但同一次点击还弹了
ArkUI 的确认框「打开外部浏览器？」，点「打开」就再开一份系统浏览器 —— 一次点击开两处。

用户判定为 bug，要求：**设置里如果是「在侧边栏打开链接」，就不要弹那个提示框。**

## 二、为什么会双开

### 2.1 上游这一侧（对的）

聊天正文的链接由上游 Markdown 渲染成 `<a target="_blank" rel="noopener noreferrer">`，其 `onClick`
自己会 `preventDefault()` 再按设置分流（`dsh-web-frontend/dist/assets/index-*.js` 里的锚点组件，
压缩后名 `rU` / `sU`；逻辑与 `dsh-client-ui-chat/lib/client.js` 的 `openExternalLink` 对应）：

```js
// 设置 store：linkOpening（"sidebar" | "new-tab"，缺省按 "sidebar"）
if (linkOpening.getSnapshot() === "sidebar"
    && ctx.get("sidebarRightTabs")?.get("browser") !== void 0)
  ctx.sidebarRight.openTab("browser", { params: { url } });
else
  window.open(url, "_blank", "noopener,noreferrer");
```

侧栏浏览器 tab 已在本档启用（`hostcore/profile` 的 `ui-sidebar-browser`，官方默认只给 desktop），
所以 `sidebarRightTabs.get("browser")` 存在 ⇒ 上游走的是**侧栏**，行为正确。

### 2.2 我们这一侧（错的）

`WebApp.ets` 的外链垫片为了修「点了没反应」（ArkWeb `multiWindowAccess=false`，`window.open` /
`target="_blank"` 一律被丢弃），在**捕获阶段**给 `document` 挂了 click 监听：看到
`a[target="_blank"]` + http(s) 就投 `openExternal(url, 'confirm')` 并 `preventDefault()`。
它**不 stopPropagation**，于是上游的 onClick 照样跑 —— 一次点击两条路都走：

| 顺序 | 谁 | 结果 |
|---|---|---|
| 1 | 壳垫片（捕获） | 弹「打开外部浏览器？」→ 用户点「打开」则系统浏览器再开一份 |
| 2 | 上游锚点 onClick（冒泡） | `preventDefault()` + 侧栏浏览器 tab 打开 |

`linkOpening === "new-tab"` 时还会更糟：捕获兜底弹一次，上游 `window.open` 又被垫片包了一层再弹一次
（两个一样的框）。

## 三、真机证据（旧版垫片，2026-11-03 13:56）

`files/diag-openlink`（ArkTS 桥落盘，带 ISO 时间戳）：

```
2026-11-03T13:56:39.646Z confirm https://github.com/fufay/whale/releases/tag/v1.1.0
```

`files/diag-web-console`（ArkWeb console 落盘）同一秒内：

```
2026-11-03T13:56:39.656Z L2 :10 [dshm-link] deliver confirm https://github.com/fufay/whale/releases/tag/v1.1.0
2026-11-03T13:56:40.948Z L4 :0 Framing 'https://github.com/' violates the following Content Security Policy
                          directive: "frame-ancestors 'none'". The request has been blocked.
```

第二行只可能来自**侧栏浏览器 tab 的 iframe**（外部浏览器不进我们 WebView 的 console）⇒「侧栏开了」
「确认框也弹了」同时成立，双开坐实。同一批日志里 13:54:31 点 baidu 后 baidu 页面 JS 正常执行，
说明侧栏 tab 本身是好的。

## 四、修法

只动壳的兜底判据：**页面自己接管过的点击，壳不再兜底。**

1. `document.addEventListener('click', …, true)` → `false`（改冒泡）：必须等页面 onClick 跑完才能读到
   `defaultPrevented`。
2. 监听体第一句：`if (ev.defaultPrevented) { return; }`。上游锚点一定 `preventDefault`，
   于是「侧栏打开」这条路上壳彻底不出手；页面**没**接管的点击（「联系我们」裸锚点、
   AccountSection 的授权锚点）`defaultPrevented` 仍为 false，照旧弹确认 / 自动外开。
3. `out()` 里给 confirm 加 1.5s 同 URL 去重（`lastConfirm`）：万一还有第二条兜底同时命中，
   不叠第二个框。

判据故意**不是**「去读设置项是不是 sidebar」：设置项在 web 侧 store 里，壳读不到；而侧栏 tab 不可用
时上游正好退化成 `window.open`，垫片的 `window.open` 包装仍接得住 —— 用「页面接管没有」做判据
自动覆盖了这两种情形。

## 六、遗留（不是本次改动引入）

侧栏浏览器 tab 是**沙箱化 iframe**（官方 Web 形态；desktop 才走 Electron `WebContents`）。
`X-Frame-Options` / CSP `frame-ancestors 'none'` 的站点（GitHub 等）在侧栏里**永远白页**（§三 第二行日志）。
这类链接只能走系统浏览器 —— 侧栏工具栏自带「在系统浏览器中打开」。若要彻底解决，得换实现
（`dsh-resource://` 直连或宿主代理），属功能课题，不在本修复范围。

## 七、回退

把 `document.addEventListener('click', …, false)` 改回 `true` 并删掉 `if (ev.defaultPrevented) { return; }`
即回到双开版本（不推荐）；或 `git revert` 对应提交后重新出包。
