# 侧栏预览的「打开方式」按类型分流（2026-10-20）

> 用户反馈：「前面做 office 连接的时候，选择默认用 wps 打开，但我发现在侧边栏预览所有文件，
> 最右侧都有个『用 wps 打开』，这个不太合理。html 网页类的，应该『用浏览器打开』；
> 其他类型的，能不能调用系统的选择 app 打开（如系统的『选择打开方式』弹框）。」

## 1. 根因（为什么所有文件都有 WPS 按钮）

侧栏文档预览的两个工具栏槽（`.actions` / `.unpreviewable`）由上游
`dsh-client-ui-sidebar-documentpreview` 对**每一个**预览 tab 渲染（owner props `{absolutePath}`）。
我们的插件 `dshm-office-system-preview` 在这两个槽里注册的组件是 `HeaderAction → WpsButton`，
而它**无条件**渲染「用 WPS 打开」—— 没有判断文件类型。

> 注意：插件只**认领**了 Office 后缀（`doc/docx/ppt/pptx/xls/xlsx/odt/ods/odp`），
> 所以正文面板只有 Office 文件用我们的实现；但**工具栏按钮**是通过槽注册的，对所有 tab 都出现。

## 2. 修法

### 2.1 插件侧：按扩展名分流

`hostcore/plugins/dshm-office-system-preview/lib/client.js` 新增 `openTargetOf(path)`：

| 扩展名 | 按钮文案 | 走的桥 |
|---|---|---|
| `doc/docx/xls/xlsx/ppt/pptx/odt/ods/odp` | **用 WPS 打开**（不变） | `openFileWithWps` |
| `html/htm/xhtml/mhtml` | **用浏览器打开** | `openWithBrowser` |
| 其余一切 | **用其他应用打开** | `openWithSystem` |

### 2.2 ArkTS 侧：两个新桥（`WebApp.ets`）

两个桥都先把文件**拷进应用沙箱**（`files/cache/open-with/`）——原因与 WPS 桥相同：
工作区文件（`/storage/Users/...`）本应用读得到，但不保证能**委托**给第三方应用；
拷进沙箱后带 `FLAG_AUTH_READ_URI_PERMISSION` 才能被目标应用读取。只拷贝，不动原文件。

| 桥 | want 形状 | 效果 |
|---|---|---|
| `openWithBrowser` | `action=ohos.want.action.viewData` + `uri` + `type=text/html` + 读写授权 | 系统按默认应用/候选拉起**浏览器** |
| `openWithSystem` | 同上，但**不传 type**（系统按 uri 后缀识别）+ `parameters['ohos.ability.params.showDefaultPicker'] = true` | **强制弹出系统「选择打开方式」弹框** |

依据：华为官方《拉起文件处理类应用（startAbility）》——
`showDefaultPicker` 为 true 时「始终展示弹框」；`type` 不传时系统按 uri 后缀匹配；
html 依赖本地其它资源时可另用 `parameters['ability.params.stream']` 授权（见 §4 边界）。

## 3. 打包与验证

- 插件随**核心树**分发 ⇒ `coreVersion` 升 `0.2.1-rc.2+whale.2`（`hostcore/core-recipe.json`），
  `pack-core` 重放 23 处补丁、复制 9 个自带插件、重新出容器；
- 装 HAP 后重启，验证三类：Office 文件 → WPS；`.html` → 浏览器；其它（如 `.pdf`/`.png`/`.md`）→ 系统选择框；
- 诊断：ArkTS 桥每次调用写 `<files>/diag-file-open`（`browser ok …` / `system ok …`），
  系统侧是否弹框看用户实测（我们无法自动点击验收）。

## 4. 边界（明确不做/暂不做）

- **html 的相对路径资源**：当前只拷主文件，页面引用的同目录 css/js/图片在浏览器里可能加载不到。
  官方为这种场景留了 `ability.params.stream`（把依赖文件的 URI 数组一起授权）——需要"整目录拷贝 +
  逐个授权"，本轮**未做**（先满足"用浏览器打开"这个主诉求；用户实际遇到缺资源再补）。
- 不新增权限、不改上游 dsh、不改任何既有目录。

## 5. 打开方式缓存的自清理（2026-10-20 用户追加要求）

用户指出：如果哪天预览/打开的是视频这类大文件，"复制进沙箱"会越攒越多 ⇒ 增加自清理。

- 每次点击「用 WPS 打开 / 用浏览器打开 / 用其他应用打开」时，先清理两个缓存目录
  `files/cache/open-with` 与 `files/cache/wps-open`（**当前正在打开的那份永远跳过**）；
- 规则（任一命中就从**最旧**开始删）：
  1. 超过 **24 小时**未使用；
  2. 单目录超过 **10 份**；
  3. 单目录总量超过 **200 MB**；
- 只删本应用沙箱里的副本，**绝不碰用户原文件**；清理失败（例如目标应用还占着）静默跳过、下次再清；
- 清理失败绝不影响本次打开（整段 try/catch）。

## 6. 为什么「侧栏预览」不需要拷贝，而「交给其他应用」需要

- **侧栏预览 = 本应用内部**：dsh Host 跑在我们 App 进程里，用 `workspaceFiles/read`（或 readBytes）
  直接读工作区文件，把**内容**经本机 HTTP 交给我们的 ArkWeb 页面渲染。文件从未离开本应用的权限域
  ⇒ 不需要跨应用委托 ⇒ 不需要沙箱副本。
- **交给其他应用 = 跨应用**：want 里的 `uri` 契约是 `file://<本应用 bundleName>/<本应用沙箱路径>`，
  系统只对这种"可委托"的沙箱 URI 授权；工作区路径（`/storage/Users/...`）不属于本应用沙箱，
  直接传会被目标应用拒绝（这正是当初 WPS/系统预览"打不开"的根因）⇒ 必须先拷一份再委托。
- 因此本插件的 `OfficeBody` 预览卡片本身**不读文件内容**，只拿到绝对路径；真正跨应用打开时才复制。
