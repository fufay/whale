# dsh-hilog · 开发需求文档（v1 草案）

> **目的**：把「抓鸿蒙 hilog」从"给人点的侧边栏面板"变成 **agent 可直接调用的 DSH 工具**。
> **来源**：2026-10-15 会话产出。**下文所有命令与输出都在本机实测过**，接手会话请照此实现，不必重新调研设备能力，也不要改写成 `node:child_process` 那套。
> **一句话**：让 AI 一次调用就拿到结构化、可信的 hilog —— 它自己控级别、自己防缓冲区滚掉、自己还原设备状态。

---

## 0. 结论先行：可行，且比想象的小

- **MVP 不需要 Web UI / client.js / typert**：纯 host 侧插件 + 2~3 个 agent 工具即可（dsh-deveco 那套侧边栏面板是它的选择，不是必须）。
- 关键依赖**逐条实测通过**（见 §2），没有"理论上应该行"的环节。
- 规模估计：`lib/index.js` 约 300–500 行 + 固定样本单测 + README ⇒ **一个新会话可完成**。
- 最大的未知不在插件本身，而在**设备可达性**（已确认当前可用，但依赖 hdc 目标状态，见 §5.3）。

## 1. 背景：为什么要做这个

### 1.1 AI 侧现状（痛点）
AI 抓一次日志要手工 5 步 shell，任一步漏掉就白抓：

```sh
hdc shell "hilog -b D"                                        # 1 提级别
hdc shell "sh -c 'timeout 25 hilog > /data/local/tmp/x.txt &'" # 2 后台边跑边落盘
hdc file recv /data/local/tmp/x.txt                            # 3 拉回
# 4 自己解析时间/级别/pid/tag/正文
hdc shell "hilog -b W"                                         # 5 还原级别
```

### 1.2 两个设备侧默认值（不是 bug，但会咬人）
| 项 | 实测值 | 后果 |
|---|---|---|
| `hilog.loggable.global` | **`W`** | 应用的 `hilog.info()` 进缓冲区前就被丢弃 ⇒ 常被误判成"代码没跑" |
| app 日志缓冲区 | **512 KB** | 约 20 秒滚掉 ⇒ 事后翻不到，必须边跑边读/边落盘 |

（这两条与 `AGENTS.md §九` 的记载一致。）

### 1.3 已有参照物与差异
- `dsh-deveco`：把这套能力做成了**给人点的侧边栏面板**（`hilogStreamStart/Read/Stop`，底层 `devecocli log --follow`）。**我们不重复造面板**。
- 我们要的是：同一能力**投影成 agent 工具**，且**不依赖 devecocli**（本机 devecocli 不在 PATH，见 `AGENTS.md §十二`），直接走 `hdc`。

## 3. 范围

### 3.1 v1 要做
| 工具 | 作用 |
|---|---|
| `hilog_level` | 读 / 设 / 还原日志级别（默认只读；设置时**必须能还原**） |
| `hilog_dump` | **非阻塞**取当前缓冲区（`-x`），支持 tag/level/pid/正则/行数过滤 |
| `hilog_capture` | 实时抓 N 秒（或抓够 M 条即停），**边读边收集**（对抗 512KB 滚动），结束自动还原级别 |

### 3.2 v1 明确不做
- ❌ 任何 Web UI / 侧边栏 / 设置页（以后再说）
- ❌ 驱动设备 UI（点击/输入/滑屏）—— 与 `AGENTS.md §十三` 的授权边界一致
- ❌ kmsg / 私有日志 / `-G` 改缓冲区大小（`-G` 是**持久化配置**，禁止碰）
- ❌ 依赖 `devecocli`

## 4. 工具契约（建议，可微调）

### 4.1 输入输出
```
hilog_level({ action: "get" } | { action: "set", level: "D"|"I"|"W"|"E"|"F" })
  → { ok, device, before, after }

hilog_dump({
  tag?,            // 单个 tag 或数组，最多 10 个（-T）
  level?,          // 级别过滤（-L），如 "I" / "IW" / "^D"
  pid?,            // 最多 5 个（-P）
  regex?,          // 内容正则（-e）
  lines?,          // 默认 200，上限硬编码（-a / -z 或客户端截断）
  device?,         // 缺省 = 自动挑唯一 Connected 目标
  save?            // true 则完整落盘，返回 filePath
})
  → { ok, device, entries:[{time,level,pid,tag,msg}], truncated, filePath?, stderr? }

hilog_capture({
  tag?, level?, seconds?=15, maxLines?=2000, regex?, device?, save?=true,
  restoreLevel?=true      // 默认 true：抓到旧级别→设新级别→跑→还原
})
  → { ok, device, entries[], truncated, levelBefore, levelAfter, filePath?, stderr? }
```

### 4.2 设备侧 hilog 开关（实测，直接照用）
| 开关 | 含义 |
|---|---|
| （无开关） | 阻塞式实时输出 |
| `-x` | **非阻塞**读完缓冲区即退出（`hilog_dump` 用它）。⚠️ 实测**不能与 `-a`/`-z` 同用**，否则报 `Mutlti commands can't be used in combination [CODE: -31]` |
| `-T <tag>` | tag 过滤，最多 10 个（`^` 前缀取反） |
| `-L <level>` | 级别过滤：`D/I/W/E/F` 或 `DEBUG/INFO/…`，可组合、可 `^` 取反 |
| `-P <pid>` | pid 过滤，最多 5 |
| `-D <domain>` | domain 过滤，最多 5 |
| `-e <expr>` | 内容正则 |
| `-a <n>` / `-z <n>` | 头 n 行 / 尾 n 行 |
| `-b <level>` | 设置 base level（提级别用；**用完要还原**） |
| `-w start -f <file> -l <size> -n <count>` | 设备侧落盘任务，文件在 `/data/log/hilog/`（长会话备选路径） |
| `-r` / `-g` / `-G` / `-s` | 清空 / 查缓冲 / 设缓冲（持久化，禁用）/ 统计 |

### 4.3 设备接入的三种情形（**别指望 USB**）

app 沙箱里 **USB 不可用**（实测 `libusb: opendir devices failed, errno=13` ⇒ `libusb_init failed`），且自己起不了 hdc server ⇒ 插件只能连"**已经在 `list targets` 里处于 Connected 的 TCP 目标**"。三种设法：

| 目标 | 怎么连上 | 用户要不要手工给 ip:port | 已知边界 |
|---|---|---|---|
| **本机 PC（自测）** | 打开「无线调试」（设备暴露 TCP 端口） | ❌ **不用**——连上后自动出现在 `list targets`，插件自动挑唯一的 Connected | 端口每次开关都变（38293/33001/33485/32791…）；关闭时只剩 Offline 残留 |
| **手机 / 平板（无线）** | 目标设备开「无线调试」→ 拿它显示的 IP:端口 → `hdc tconn <ip>:<port>` | ⚠️ **第一次 / 端口变了之后要一次**（tconn 之后插件就能自动发现，不必每次抓日志都报一遍） | 端口会变；手机侧必须开无线调试 |
| **手机 / 平板（USB，免无线）** | 宿主终端 `hdc -s 127.0.0.1:18710 start` 且 USB 插着目标 → 沙箱侧用 `hdc-via-host.sh`（借宿主 server） | ❌ 不用给 ip:port，但要**宿主那条 server 一直开着** | ⚠️ **v1 必需**：插件默认 spawn 的 `$HOME/bin/hdc` 走的是**桥（无线）**路径，而**桥看不到 USB 设备**（实测见下）⇒ 必须让 hdc 命令**可配置**，否则插件对手机/平板根本用不了 |

**对照实验（2026-10-15 10:45 实测，把这条结论钉死）**：宿主 `hdc -s 127.0.0.1:18710 start` 已开（18710 可连接 ✅）、无线调试**关闭**（32791 Connection refused）⇒

- 桥路径 `hdc list targets -v`：只剩历史端口的 Offline 条目，**无 Connected**，并打出提示
  `[hdcb] 无法连接本机 hdc：请确认「设置→开发者选项→无线调试」已开启`；
- 借宿主 server 的 `hdc-via-host.sh list targets -v`：shim 正常挂上（`UDS → TCP 127.0.0.1:18710`），结果 **`[Empty]`**。

⇒ **宿主 server ≠ 有设备**：它只提供"服务端点"，而本机 PC 不是自己的 USB 外设 ⇒ **本机自测必须开无线调试**；18710 那条路只对插在宿主 USB 上的手机/平板有效（那时 shim 才会显示 `USB Connected`）。桥的提示文案很明确，插件可直接透传给用户（正好满足下面第 2 条）。

**USB 手机实测（2026-10-15 10:47，PLR-AL50 插在宿主 USB、手机与 PC 的无线调试均关闭）**：

- 借宿主 server：`hdc-via-host.sh list targets -v` → **`5BH0225304025535  USB  Connected  localhost`** ✅
- 桥路径（对照）：`hdc list targets -v` → **只有一堆 Offline 的 TCP 残留，看不到这台手机** ❌
- 设备身份：`PLR-AL50` / API `26` / `7.0.0.109(SP6C00E105R7P3)`；`hilog.loggable.global` 同样是 **`W`**
- 流式抓取：`hdc-via-host.sh -t <key> shell "timeout 6 hilog -L W"` → **真实日志正常流回** ✅

⇒ **"借宿主 server"不是可选项，而是抓手机/平板日志的唯一现实通路**（本机 PC 自测仍走无线调试）。`Config` 必须有 `hdcCmd`（默认 `hdc`；手机场景指向 `hdc-via-host.sh`）。

⇒ 由此得出三条硬要求：
1. **插件绝不能要求"每次抓日志都手输 ip:port"**：默认自动挑 Connected；只在 `tconn` 这一步需要用户给一次（或宿主代劳）；建议额外提供 `hilog_devices`（列出目标）与 `hdc_connect({ip,port})`（代跑 tconn + 刷新）两个轻量工具，让"给一次"这件事在对话里完成。
2. 检测不到 Connected 目标时，报错必须**带上 `list targets -v` 原文 + 明确指引**（"请开无线调试"或"请先 tconn ip:port"），不能静默空返回。
3. ⭐ **双通道自动探测（省掉"这次走哪条路"的人工决策）**：先用 `Config.hdcCmd`（默认 `hdc` = 桥/无线）取目标；若没有 Connected、或调用方显式要求 USB 设备，则自动改用 via-host 命令（`hdc-via-host.sh`）再试一次；**返回值里注明本次走的是哪条通道**（`channel: "bridge" | "via-host"`）。
   ⇒ 用户只需做两件事：**PC 自测时保持无线调试开着**；**调 USB 设备时让宿主 server 活着**（一条 `host-server-keepalive.sh` 即可常驻，见 §7 参考实现）。之后**不需要告诉 AI "这次走哪条路"**。

⛔ **不要在插件里尝试"自己起宿主 server"**（2026-10-15 实测，三道墙，省得白写代码）：
1. `/bin/sudo` 虽是 setuid-root 真二进制，但在沙箱里跑直接 `init challenge failed`（凭据机制依赖沙箱拿不到的 HUKS —— 与当年 hdc 需要伪造 HUKS 同源）；
2. 即便有 root 也**看不到 USB**：`ls /sys/bus/usb/devices` → Permission denied（SELinux `u:r:develop_tools_debug_hap:s0`），这正是 `libusb: opendir devices failed, errno=13` 的根因；
3. 即便有 root 也**起不了 server**：它要 bind `/data/hdc/hdc_debug/…`，而该路径在沙箱挂载视图里**根本不存在**。

⇒ 插件的能力上限是：**探测通道 + 精确指引**（"请开无线调试" / "请在宿主跑这条命令"），不是自动提权。

### 4.4 输出纪律（**这条决定工具好不好用**）
- **默认只回摘要 + 前 N 条**（建议 N=200 行或 32 KB，谁先到算谁），完整日志写文件：
  `Build/dsh-hilog/logs/<时间戳>-<tag>.log`（工作区内、可被后续会话读取）。
- 返回值必须带 `truncated` 标志与 `filePath`，让 AI 知道"还有多少没看"。
- 绝不把整个 512KB 缓冲区一次灌进对话。

## 5. 实现约束（都是踩过的坑）

1. **级别必须 `try/finally` 还原**：读到旧值 → 设新级别 → 干活 → 还原。否则给设备留下 D 级噪音（`AGENTS.md §九`）。
2. **不要用 `hilog > file &` + `timeout` 那套 shell 权宜写法**：用常驻子进程**流式读取**（读完即处理，天然不怕 512 KB 滚动）；长会话可用 `-w start` 落盘后取文件。
3. **设备选择**：`hdc list targets -v` 实测会列出**多条 Offline**（本次 5 条，仅 1 条 Connected）。必须自动挑 `Connected`，或让调用方显式指定。⚠️ `hdc shell` **不带 `-t` 会打到错误目标**（实测报 `errNum is:1002`）。
4. **一律走 `ctx.shell`**，命令与参数分离传递（不拼字符串；设备路径/文件名可能含空格或中文）。
5. **超时与取消**：默认 ≤15 s；工具被取消或抛异常时，也要还原级别 + 杀干净子进程（不能留孤儿）。
6. **解析要稳**（真机样本见附录 C）：
   - 实际行格式：`MM-DD HH:MM:SS.mmm  pid  tid  L  domain/pkg/tag: msg` —— **pid 后面还有 tid 两列**；tag 字段可能带 `/`（如 `A01B07/com.ohos.sceneboard/IMKG`），别按"tag 里没有斜杠"写正则；
   - **必须过滤 shim 噪声行**：走 `hdc-via-host.sh` 时，输出流每次都会多一行 `[hdc-tcp-shim] UDS … -> TCP 127.0.0.1:18710 (fd N)`（实测），不过滤会污染解析与计数；
   - **阻塞读会先吐缓冲区历史**（实测 `hilog -L W` 的第一行是几天前的旧日志）⇒ 若要"只看新日志"，按本次调用起始时间戳过滤；**绝不要用 `-r` 去清缓冲区**（那是破坏性操作，会影响别人）；
   - 用**固定样本**做单测（无需设备）。
7. **失败要可诊断**：把 hdc 的 stderr 原样带回返回值（别吞）。
8. **安装与重启**：装完**必须重启 DSH** 才挂载；安装前后各跑一次 `precheck`（`AGENTS.md §二`：本机有两次"profile 被写坏 ⇒ 应用起不来"的前科）。
9. **别把"设备睡了"误判成"插件坏了"**：熄屏/空闲时 hdc 连接照样在（实测：USB 手机熄屏后仍 `USB Connected`，`hilog -z 2` 照常出、时间戳就是当下），但**日志量会趋近于零**（后台应用被系统冻结/挂起）⇒ `capture` 返回里应带**可能原因提示**（例如"条目数极少且无目标 tag 命中 ⇒ 设备可能息屏/空闲，或目标应用已被冻结"），并让 `Config` 能放宽时长。想熄屏也照跑，属于设备侧设置（开发者选项「充电时屏幕不休眠」）或应用侧长时任务，不是调试通道问题。

## 6. 验收标准

### 6.1 单测（沙箱内可跑，不需要设备）
hilog 行解析（普通/`-v long`/含中文/含空格）、设备挑选（多 Connected / 全 Offline）、级别还原路径、输出截断、参数拼接（含空格与中文）。

### 6.2 真机验证（只读，允许；**不做模拟用户操作**——见 `AGENTS.md §十三`）
1. `hilog_level get` ⇒ 返回 `W`
2. `hilog_dump` ⇒ 返回缓冲区已有条目（非空）
3. `hilog_capture({seconds:10, tag:"<某个正在跑的应用的 tag>"})` ⇒ 结束后 `hilog_level get` **必须回到 `W`**（这一步是"还原生效"的硬证据）
4. `save:true` 时，落盘文件存在，且行数与返回摘要一致
5. 故意传错 `device` ⇒ 返回可读错误 + hdc stderr，而不是挂死

## 9. 待定问题（实现前先拍板）

1. **要不要三段式 `hilog_start/stop/read`**（长会话边跑边看）？v1 建议只做一次性 `capture`，够用且简单。
2. **要不要复用 `devecocli log`**？v1 建议**不依赖**，纯 hdc（本机 devecocli 不在 PATH）。
3. **默认输出上限**取多少（200 行 / 32 KB）？建议做成 `Config` 可调，默认保守。
4. **是否附带"帮用户看某个应用的日志"预设**（如按包名反查 pid：`hdc shell pidof <pkg>`）？建议 v1 先只接 `pid`，包名映射留 v2。
5. **要不要加 `hilog_devices` / `hdc_connect({ip,port})`**（把"给一次 ip:port + tconn"收进对话里，之后自动发现）？建议加，成本很低，且直接消灭"每次都要手报端口"的体验问题。
6. **hdc 命令是否做成可配置**（`Config.hdcCmd`，默认 `hdc`）？建议 v1 就留这个口子：指向 `hdc-via-host.sh` 即可支持"USB 手机免无线调试"那条路（见 §4.3 表格第三行）。**注：本节问题 6 已由实测升级为 v1 必需项，见 §4.3 的"三条硬要求"第 3 条。**
